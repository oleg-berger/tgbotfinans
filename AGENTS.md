# Инструкции по работе с проектом

## Назначение и стек

Проект — Telegram-бот личного учета финансов в KZT. Пользователи работают в личных чатах; каждый Telegram ID имеет отдельные банки, категории, операции и настройки. Регистрация автоматическая, списка разрешенных пользователей нет. Веб-интерфейса и интеграции с банковскими счетами нет.

Стек: Python 3.12+, asyncio, aiogram 3, aiosqlite, SQLite, python-dotenv, zoneinfo с tzdata. Зависимости закреплены точными версиями в `requirements.txt`; тестовые зависимости — в `requirements-dev.txt`. `pyproject.toml` содержит метаданные и настройки pytest, но не конфигурацию сборки пакета или линтера.

Альтернативный запуск на Cloudflare Workers Free: небольшой JavaScript frontend и приватный Python 3.13 Durable Object с SQLite. Код и настройки — в `cloudflare/`, зависимости SDK/tzdata закреплены в его `pyproject.toml`/`uv.lock`, Wrangler — в `package-lock.json`. Прикладные модули общие; локальный запуск сохраняется. Публикация, установка webhook и перенос рабочих данных — отдельные явно запрошенные действия.

## Архитектура и границы модулей

Путь пользовательского события:

```text
Telegram → runtime.make_router() → Application.handle()
         → Database.atomic() → Session / Views → Ledger → SQLite
         ← runtime.deliver() / редактирование сообщения ← Screen
```

| Файл | Ответственность |

Сохраняйте эти границы: финансовое правило добавляется в `Ledger`, разбор ввода — в `parsing.py`, сценарий — в `Session`, экран — в `Views`, взаимодействие с Telegram — в `runtime.py`. Возвращайте `Screen`, а не объекты aiogram, из прикладного слоя. Не вводите ORM, веб-сервис, отдельный FSM aiogram или дополнительные слои без задачи, которая это требует.

## Хранение, атомарность и повторные события

- `Database.transaction()` использует `asyncio.Lock`, отдельное соединение, `foreign_keys=ON`, `busy_timeout=5000` и `BEGIN IMMEDIATE`. При исключении, включая отмену задачи, выполняется rollback.
- `Ledger` получает готовое соединение. Он не открывает собственные транзакции и не делает commit: транзакцией владеет вызывающий код.
- Общий интерфейс хранилищ: `atomic(action)` и `savepoint(conn, action)`. На Cloudflare await внутри финансовой транзакции обязан завершаться синхронно: разрешены только вызовы SQL-моста. `complete()` отклоняет реальное асинхронное ожидание и откатывает транзакцию. Сеть, таймеры и фоновые задачи внутри транзакции запрещены.
- `Application.handle()` сохраняет изменения операций, диалога и сериализованный ответ в `events` одной транзакцией. Повтор `(user_id, event_key)` возвращает сохраненный ответ. Сохраняйте эту атомарность.
- Ключи транспорта: `m:{chat_id}:{message_id}` для сообщений и `c:{callback_id}` для callback. Одинаковый текст с разными ключами — разные события.
- Внутри обработки используется `SAVEPOINT action`: ошибка валидации откатывает действие, после чего сохраняется экран с ошибкой. Неожиданное исключение откатывает всю транзакцию.
- Доставка ответа Telegram происходит после commit и может завершиться ошибкой отдельно. Не переносите сетевую отправку в транзакцию пользовательского события.
- События старше 30 дней удаляются обслуживанием; дедупликация по `events` не бессрочна.
- Таблицы: `users`, `banks`, `categories`, `aliases`, `operations`, `rates`, `dialogs`, `events`, `reminders`, `daily_reminders`; `schema_version` хранит версии миграций.
- Все обращения к пользовательским объектам проверяют владельца через `uid`/`user_id`. ID из callback не доказывает право доступа. Для нового ввода проверяйте также `active=True`.
- Значения SQL передаются параметрами `?`. Динамические имена таблиц/столбцов допустимы только из контролируемых вариантов, как в существующих методах.
- Изменения схемы добавляйте новой версией в конец `MIGRATIONS`; не переписывайте примененные миграции. Сейчас есть версии 1–5; неизвестная более новая база отклоняется при старте. Версия 4 добавляет `guide_completed` и `cashback_intro_shown`; существующие пользователи с банками считаются прошедшими знакомство. Версия 5 индексирует даты `events` и `daily_reminders`, чтобы минутная очистка не сканировала всю историю и не расходовала квоту Cloudflare. Снимки версии 4 совместимы с версией 5: столбцы не изменились.
- При добавлении пользовательской таблицы обновляйте `reset_user.USER_TABLES`, порядок удаления и тесты сброса: утилита проверяет точное совпадение списка таблиц.
- Проверяйте миграции как на новой базе, так и на базе предыдущей версии. Для этого используйте временные базы.

## Финансовые инварианты

- Деньги хранятся целыми тиынами: 250 ₸ = `25000`. Не используйте `float`. Проценты хранятся десятичными строками; расчет выполняется через `Decimal`, округление кэшбэка — `ROUND_HALF_UP` до тиына.
- В пользовательской обычной записи сумма положительная, без знака и разделителей тысяч, максимум два десятичных знака. Доход/расход определяется категорией. Нулевые и отрицательные суммы разрешены для начального остатка и корректировки.
- Даты операций хранятся как `YYYY-MM-DD`, месяцы как `YYYY-MM`; пользователь вводит дату `ДД.ММ.ГГГГ` второй строкой. Запрет будущей даты проверяется относительно локального дня пользователя в сценариях ввода.
- Часовой пояс по умолчанию — `Asia/Qyzylorda`; настройки принимают IANA timezone. Время приложения и служебные отметки — aware datetime в UTC, пользовательский день вычисляется через `ZoneInfo`.
- Остаток вычисляется по неудаленным операциям, включая архивные банки. Перевод уменьшает источник и увеличивает получателя, сохраняя общий баланс. Отрицательный остаток разрешен.
- `opening` влияет на баланс и входит в доходы статистики за месяц операции и за все время со своим знаком. В отчете доходов он сгруппирован отдельно как «Начальный остаток», с маршрутом `ops:{month}:opening:{page}`. `adjustment` и `transfer` влияют на остатки, но исключены из доходов/расходов статистики. Сверка записывает разницу с расчетным остатком; изменение старых операций затем меняет остаток снова.
- Операции удаляются логически (`deleted=1`). Архивирование банка/категории сохраняет историю, убирает ключи и запрещает новый ввод. Системные категории `other` («Прочее») и `cashback` («Кэшбэк») не архивируются.
- Ключи банков и категорий разделяют одно пространство на пользователя. Нормализация — `casefold()` и схлопывание пробелов; имена тоже являются ключами. Разбор поддерживает многословные ключи и выбирает самое длинное совпадение.
- Неизвестные слова запускают диалог привязки/создания; операция не сохраняется до завершения выбора. Сохраняйте исходный текст и `original_today`, чтобы продолжение после перезапуска не меняло дату записи.
- Первый банк автоматически становится банком по умолчанию. При создании следующего пользователь выбирает, менять ли основной банк. После архивирования основного банка выбор сбрасывается.
- Ставка кэшбэка привязана к пользователю, банку, категории расходов и месяцу. `None` означает отсутствие настройки, строка `"0"` — настроенные 0%.
- Покупка сохраняет свою ставку. Изменение только суммы сохраняет ставку; смена банка, категории или месяца берет актуальную ставку нового сочетания. Пересчет старых покупок при изменении/копировании ставок зависит от выбора пользователя.
- Ожидаемый кэшбэк не входит в остаток. Выплата — отдельный доход с `payout_month`; допускается одна неудаленная выплата на пользователя, банк и месяц покупок, что защищено уникальным индексом. Повторный `Ledger.payout()` возвращает существующую операцию. Изменения покупок не изменяют сумму выплаты.
- Кнопка `paynow` в текущем интерфейсе зачисляет ожидаемую сумму текущей датой сразу. Сценарий `payout` позволяет указать фактические сумму и дату. При изменении этой части сверяйте код, гайд и README: их формулировки должны соответствовать поведению.
- CSV сохраняет UTF-8 с BOM, разделитель `;`, десятичную запятую и защиту пользовательских текстовых полей от формул таблиц.

## Диалоги и интерфейс

- Диалог хранится в SQLite как JSON с `step`, `token`, `data`; состояние и страница гайда переживают перезапуск. Не заменяйте это хранением только в памяти.
- `begin()` создает новый 12-символьный токен; `advance()` переходит через `begin()`. Кнопки диалога имеют вид `d:{token}:{value}`, а выбор проверяется относительно текущего сохраненного токена.
- Остальные маршруты — строки с разделителем `:`: например, `obj:bank:{id}`, `stats:{month}`, `ops:{month}:{category}:{page}`. Согласованно обновляйте генерацию маршрутов и обработчики.
- Сохраняйте совместимость сериализации `Screen` с уже сохраненными ответами. Новым необязательным полям задавайте значения по умолчанию; документы сериализуются через base64, фото — относительным путем внутри `financebot`.
- Telegram использует HTML parse mode. Экранируйте пользовательские значения через `html.escape` на границе отображения. Подписи кнопок — обычный текст, HTML в них не нужен.
- Интерфейс и сообщения валидации — на русском, с принятыми эмодзи и форматом сумм `1 234,50 ₸`. Технические идентификаторы — на английском.
- Используйте существующие `buttons()` и `pages()`; стандартный размер страницы — 8. У длинных списков должны оставаться доступными пагинация и возврат.
- `/start` открывает приветствие и гайд, сохраняя финансовые данные. Новый пользователь завершает семь страниц, создает первый банк и получает предложение настройки первого кэшбэка. Прогресс хранится в `users`; повторный гайд не сбрасывает его и не повторяет предложение. Создание категории из меню возвращает главное меню. Для нового сценария сохраняйте работающие выходы в меню и отмену.
- В polling используется `handle_as_tasks=False` для последовательной обработки и доставки. Меняйте модель конкурентности только с учетом порядка сообщений, транзакций и диалогов.

## Стиль кода

- Следуйте стилю соседнего модуля: четыре пробела, `snake_case` для функций/переменных, `PascalCase` для классов, `UPPER_CASE` для констант, преимущественно двойные кавычки и относительные импорты внутри `financebot`.
- Код компактный и процедурный: ранние возвраты, обычные словари для записей и состояний, небольшие вспомогательные функции, `dataclass` для простых структур (`Config`, `Entry`, `Screen`).
- Типизация выборочная: в парсере и структурах есть аннотации, во многих обработчиках их нет. Добавляйте полезные аннотации при изменении интерфейсов, без массового переписывания существующего кода.
- В проекте встречаются длинные строки SQL и выражений; жесткий лимит длины строки и автоматический форматтер не настроены. Не переформатируйте файлы целиком ради небольшого изменения.
- Docstring модулей и технические комментарии обычно на английском, краткие и объясняют ограничения/причины. Не добавляйте комментарии, которые повторяют очевидный код.
- Ожидаемые ошибки ввода оформляйте как `ValidationError` с понятным русским сообщением; для неизвестных ключей используется `UnknownWords`. Не маскируйте неожиданные ошибки как успешное действие.
- Не добавляйте зависимости и широкие рефакторинги без необходимости. При изменении пользовательского поведения обновляйте соответствующие тексты README, помощи и гайда.

## Проверки

Выполняйте команды из корня проекта. На Windows используйте существующее окружение:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m compileall -q financebot
```

Для подготовки нового окружения: `py -3.12 -m venv .venv`, затем `.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt`. На Linux эквивалентный интерпретатор — `.venv/bin/python`.

`pytest` настроен в `pyproject.toml`: `asyncio_mode = "auto"`, `testpaths = ["tests"]`, `pythonpath = ["."]`. Асинхронные тесты и фикстуры не требуют отдельного `@pytest.mark.asyncio`.

| Тестовый файл | Что проверять при изменении |
| --- | --- |
| `tests/test_finance.py` | Парсер, точность денег, балансы, ставки/выплаты, редактирование, ключи, изоляция и CSV. |
| `tests/test_application.py` | Сценарии через `Application.handle()`, дедупликация, rollback, подтверждения, устаревшие callback, меню и настройки. |
| `tests/test_guide.py` | Семь страниц, иллюстрации и сериализация, продолжение после перезапуска, создание категорий. |
| `tests/test_jobs_runtime.py` | Локальное время напоминаний, повтор доставки, очистка событий, восстановление и ротация копий, конфигурация. |
| `tests/test_transport.py` | Настоящий диспетчер aiogram с подменой только HTTP Telegram, игнорирование групп и межпроцессная блокировка. |
| `tests/test_reset_user.py` | Предпросмотр, изоляция сброса, восстановление из копии, запрет удаления при ошибке копирования/занятой базе. |

Фикстуры создают базы в `tmp_path`; время фиксируют через `Application(..., clock=...)` или `Maintenance.tick(now=...)`. Добавляйте проверки изменяемого поведения и финансовых рисков на этом же уровне, используя соседние тесты как образец. Не привязывайте тесты к реальному токену, сети или текущей дате. Для изменения только документации новые тесты не нужны.

`python -m financebot --check` проверяет формат конфигурации без Telegram; не доказывает действительность токена. Проверка с настоящим ботом проводится отдельно по сценарию ручной приемки в README.

## Эксплуатация и данные

- Не читайте и не выводите содержимое `.env`, реальных баз `data/` и резервных копий для обычной разработки. Для схемы и правил достаточно исходников и временных тестовых баз.
- Не добавляйте в коммиты токены, финансовые данные, `.venv`, SQLite/WAL/SHM, копии и локальные логи. Ориентируйтесь на `.gitignore` и `.dockerignore`.
- Логи приложения выводят типы исключений; не логируйте финансовые сообщения, токены, полные сетевые URL или traceback с пользовательскими данными.
- Один экземпляр бота на токен; `InstanceLock` защищает только одну локальную базу. Запуск бота и перезапуск рабочего сервиса не нужны для обычного изменения кода или документации.
- Обслуживание выполняется раз в минуту. Месячное напоминание — после 09:00 первого числа по времени пользователя, с догоняющей доставкой только для текущего месяца. Оно требует завершенного гайда, показанного первого предложения кэшбэка и активного банка. Первое предложение помечает текущий месяц в `reminders` доставленным, чтобы не дублировать его фоновым уведомлением. Ежедневное напоминание по умолчанию выключено.
- Отметка доставки напоминания записывается после отправки. Сбой между отправкой и отметкой может дать повтор; не заявляйте гарантию строго однократной доставки Telegram.
- Копирование живой SQLite выполняется через Backup API с `integrity_check`, не простым копированием основного файла WAL-базы. Автоматическая ротация сохраняет семь `finance-YYYY-MM-DD.sqlite3`; копии `before-reset-*` не ротируются.
- Сброс пользователя и восстановление рабочей базы выполняйте только по явному запросу. Для сброса сначала предварительный просмотр, остановленный бот и проверка ID/пути; удаление начинается только после успешной полной копии.
- Docker использует Python 3.12, UID/GID `10001`, bind mounts `data/` и `backups/`; Compose переопределяет пути из `.env` на `/app/data/finance.sqlite3` и `/app/backups`. Входящие HTTP-порты не нужны.
